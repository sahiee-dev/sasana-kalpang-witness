## Edit-history purge probe (A8+E), observed in this run

> **Observed behaviour, dated 2026-10-21.** Everything below about GitHub's edit history (what the web UI offers, what the GraphQL schema exposes, what a deleted revision leaves behind) was observed on that date, on one comment, in one run. GitHub's UI and API behaviour may change; treat any of it as **VERIFY** on a later date.

* GraphQL schema introspection (`work/artifacts/github/introspection.json`): no mutation whose name contains edit/revision/history. The only matching type is `UserContentEdit`. So there is no *API* way to delete a revision (observed for this schema, today).
* Web UI, logged in as the comment author who is also the repo owner: the creation revision's "Viewing edit" dialog offered **Delete revision**; an in-page confirm said "This edit's content will no longer be visible. This action can not be undone." The deletion was performed through the web UI (browser session), not through the PAT.
* After deletion, GraphQL `userContentEdits` (`history_X_div_after_purge.json`): totalCount stays 2; the creation revision remains listed with `deletedAt=2026-10-21T15:56:18Z`, `deletedBy=sahiee-dev`, and its diff is now the 7-character placeholder `"deleted"` (SHA-256 `1185f37d33b0f89e..`). Before deletion its diff hashed to the substituted body. The UI dropdown still says "Edited 1 time" and marks the revision "Deleted" (`ui/history_dropdown_after_purge.jpg`).
* Conclusion for this run: the revision *content* is purgeable by the author/admin; the *existence* of an edit and of a deletion is not purged. The fresh REST read after the purge is unchanged (`fresh_post_purge.json`: IN-BOUNDS, `updated_at` 2026-10-21T15:54:13Z).
* Not tested: deleting the most recent revision; deleting and recreating the whole comment; an org/enterprise audit log (this is a personal-account repo); whether GitHub support retains purged content. **VERIFY** any claim about these.
